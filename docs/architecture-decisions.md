# Architecture Decisions

This document records decisions that shape the project and the reasons behind them. Specific libraries and versions are an initial baseline and can be upgraded or replaced when a better implementation preserves these constraints.

## Providers Are Explicit Application Dependencies

One provider is selected when the application starts and is injected into the application controller. The provider owns session discovery, transcript normalization, new and resumed session launch preparation, historical branch semantics, and interpretation of provider-specific terminal output. The application core owns graph construction, navigation, rendering, process lifecycle, and relationship persistence.

Session and message identifiers are opaque provider strings. The core must not assume UUIDs, provider CLI flags, transcript payload formats, or a particular branching implementation. Historical branch results expose validated parent-to-child message correspondence so the graph can merge shared history without understanding how the provider created it.

Branching is an explicit capability. A provider that cannot branch through a supported interface must report that limitation rather than editing transcripts or simulating fragile terminal input. Claude Code and Codex are shipped providers, and only one provider's sessions appear in a given application invocation.

## Stock Agent TUIs Run In Owned PTYs

Each live branch is a normal interactive provider process attached to its own pseudo-terminal and terminal emulator state. The application forwards input to the selected process and continues consuming output from every hidden process. Keep hidden emulators transparently composed beneath the navigator so provider-specific screen observers continue receiving updates without exposing another terminal surface.

Only the selected emulator is rendered. Switching views must not suspend or recreate unrelated agent processes.

Every in-memory terminal owner receives an immutable owner ID before acquisition begins. That ID, rather than the provider session ID, identifies the resource bundle and every asynchronous callback for its lifetime. Session IDs may move during provider-native identity adoption; owner IDs never do. Sequence terminal events as well so a delayed callback from an earlier state cannot mutate a replacement owner that happens to use the same session ID.

Opening a terminal is a transaction across persisted ownership and runtime resources. Reserve the provider session first, acquire provider-specific resources in a dedicated scope, create the emulator and PTY, register the owner synchronously after spawn, persist the process group, and only then give it focus. Roll back in reverse when any stage fails. If process-group registration or cleanup cannot be verified, retain the persisted reservation and expose cleanup-incomplete state instead of permitting a second owner.

This preserves the complete stock-agent experience and avoids maintaining a partial clone of its UI. It also rules out tmux and Herdr-style visible panes as the primary architecture.

The generic terminal manager executes provider-prepared commands and delegates activity and draft observation to a provider-created terminal observer. The initial implementation uses Bun's native PTY API with OpenTUI's `EmbeddedTerminalRenderable`, which uses Ghostty's VT parser. This combination has been validated in the development environment, but the ownership model is more important than those particular dependencies.

## Provider APIs Are Session Tools, Not The Chat Runtime

Use supported provider APIs for session discovery, message reads, and historical forks. For the Claude adapter, historical branching is based on `forkSession(sessionId, { upToMessageId })` rather than direct transcript manipulation. For Codex, short-lived `codex app-server --stdio` processes perform thread listing, reading, and forking; interactive work remains in the stock `codex resume <thread-id>` TUI.

The packaged SDK and CLI baseline is `@anthropic-ai/claude-agent-sdk` 0.3.251 with Claude Code 2.1.251. Upgrade the pinned SDK deliberately and verify session compatibility. Do not version-gate an externally installed Claude Code executable: metadata reads and historical forks use the pinned SDK, and every created fork must pass strict copied-prefix validation before its ancestry is saved. For Claude forks, validate each copied record through the SDK-imported child's explicit `forkedFrom` provenance and exact payload rather than assuming the SDK's reconstructed active transcript has the same length. If a changed transcript format prevents that validation, preserve the created child as an independent session rather than guessing its relationship.

The packaged and validated Codex baseline is 0.150.1. Do not version-gate an externally installed Codex executable: app-server responses are strictly validated, unsupported protocol changes fail the affected operation, and every historical fork must preserve its copied prefix exactly before ancestry is saved. One refresh batches all transcript reads through one app-server process, and every metadata operation closes its process after a bounded wait.

Distinguish ordinary request failure from mutation ambiguity. A provider mutation may have committed once its request was sent even if its response times out, the transport closes, or the returned child identity is invalid. Never retry such a mutation automatically. Return an explicit ambiguous outcome, perform a full provider snapshot reconciliation, and do not invent ancestry or launch a guessed child. Reads and requests proven not to have been sent may still use bounded retries. This rule applies to both Claude `forkSession` and Codex `thread/fork`.

Codex does not allocate or persist a new thread until its first user turn, so a fresh thread cannot be handed to `codex resume`. New Codex sessions instead launch the stock TUI against a dedicated authenticated loopback app-server and let the TUI call `thread/start` when the user submits that turn. The application initially owns that terminal under a temporary ID, then replaces it with the real ID reported by the sidecar's loaded-thread API. The terminal manager cleans up the sidecar with the TUI. Once the first turn is persisted, normal discovery and later resume use short-lived metadata operations and the ordinary local TUI path.

Locally prepared sessions are an immediate overlay on the last provider snapshot. Project them into the conversation forest and establish their navigator destination before activating their terminal, including when the provider has not persisted or discovered them yet. Returning from a terminal must reveal that local graph synchronously; provider refresh reconciles metadata and transcripts afterward rather than deciding which navigator view appears. Temporary-to-provider ID adoption updates terminal ownership and the local graph projection as one transition.

Identity adoption is forward-only because the provider has already changed identity before the application observes it. Commit the temporary-to-provider replacement in the unified provider-state transaction: move the persisted owner while preserving its owner token, replace every relationship, removal, and per-instance navigation reference, save any validated relation, and append a pending-adoption journal record. Only then update the in-memory owner's session aliases and notify the application actor. Acknowledgment removes the journal record after the actor has projected the new identity. An uncertain local commit reserves both identities, is retried or reconciled from the journal, and stops the terminal if ownership cannot be proven; it must never rename the provider back or roll an acknowledged move backward. Adoption onto another live owner fails closed.

Forked sessions do not include the source session's file-history snapshots. A historical conversation fork therefore does not provide historical file rewind. Because all branches share the current working tree, it also does not restore files to their state at the selected message.

## Relationships And Navigator State Need Application Metadata

Claude sessions are persisted independently. Historical forking remaps message UUIDs and does not retain enough source-branch information for this application to reconstruct a reliable cross-session tree later.

Store only the missing relationship data: the child session, parent session, source message, and validated correspondence between shared parent and child messages. Treat that correspondence as retained evidence in both directions when a later compaction omits mapped records, and reconcile restored logical paths transactionally so contradictory metadata cannot partially mutate a family graph. Persist navigator-removal and current-view records as application-owned UI state. Keep them outside the repository under the user's XDG state directory, scoped by canonical project and provider identity.

Persistence schema v3 is one strict provider-state document containing shared relationships and removals, navigation records keyed by application instance, terminal owners, and pending identity adoptions. All reads and writes use one cross-process transaction lock, semantic validation, canonical ordering, and atomic replacement with file and directory durability. Relationships, removals, ownership, identity journals, and every navigation reference can therefore move together without partially updating the provider state.

Schema v3 is deliberately reset-only while the product is in alpha. Reject v1, v2, unknown, non-canonical, and structurally or semantically corrupt documents in place. Also reject the old separate lease layout. Do not automatically migrate, delete, quarantine, or overwrite incompatible state; preserve it and require the user to move or remove it explicitly. A lock or owner is reclaimable only when liveness is definitely absent. Permission failures and unknown liveness retain ownership.

Relationships and removals are shared by all invocations for the same project and provider. Navigation is not: each foreground process receives an application-instance ID and may read or replace only its own navigation record. Concurrent invocations must not move each other's cursor, selected family, or terminal-return destination. A new process does not silently adopt another instance's navigation record.

Apply navigator removals after constructing the complete graph so relationship and message-alias resolution still use intact provider history. Prune only the selected tree or the selected node and its visual descendants from the navigator. Never edit or delete provider transcripts to implement removal.

Sessions and forks not created or recorded by `claude-tree` should still be usable. When their ancestry cannot be established reliably, show them as independent roots rather than guessing from message content.

## Claude User Messages Replay From The Previous Agent

Forking an agent message copies the transcript through that exact SDK message. Forking a user message has different semantics: copy through its nearest earlier agent, then open the child with the selected user text in Claude's composer without submitting it. Transcript order is authoritative, and adjacent messages may have the same role.

A user replay with no agent ancestor copies a zero-message prefix but remains in the same conversation family. The graph represents all top-level roots as children of one synthetic empty-history origin. That origin is application state rather than a Claude message or session: it is never rendered, selected, counted, or used as a fork target, and no connectors are drawn from it.

User replay initializes the stock Claude composer through `--prefill` rather than timing simulated PTY keystrokes. Prompts that cannot be represented as text fail closed rather than silently losing content.

Claude Code does not expose semantic composer state. The application may show a conservative, in-memory preview parsed from the visible input box when leaving a live terminal, but it must mark that preview as approximate and never persist it as transcript or relationship state.

Observe both stages of Claude's native rewind dialog: message selection and restore confirmation. The visible dialog supersedes any provisional cancelled-send or earlier rewind target, including when opened through a provider shortcut rather than a typed command. Preserve the pending restore across confirmation-screen redraws after Enter; otherwise the restored composer is missed until the next submission. Escape cancels that pending observation. Only capture the restored composer after leaving the dialog; dialog selections are not submitted prompts. Recognize the pinned CLI's separate Rewind heading and restore instructions, including bordered and wrapped confirmation screens.

Claude's native restore can change only its in-memory path until a new transcript record is appended. Repeated SDK reads of the old path cannot resolve that live boundary. Observe conversation-restore occurrence separately from the restored composer and target resolution: emit one sequenced Rewind observation after a confirmed restore exits its dialog, even if the composer is empty or unreadable. Distinguish one-stage restore-and-fork message selection from two-stage restore confirmation; the word "fork" in that dialog is not evidence of a new persisted session identity. Interpret restore actions only in the confirmation stage, never from historical prompt text. Exclude complete composer boxes from dialog recognition.

Claude Code also does not expose semantic generation state to its terminal host. Observe its OSC terminal-title activity indicator directly from PTY output so hidden processes remain observable, with conservative matching against the last visible Claude screen as a fallback. Claude versions that pin an idle title under terminal multiplexers may still be working; a live bottom-screen working footer overrides that stale title, while a visible composer remains idle. Recognized permission and input prompts are blocked rather than working. Render a blocked live endpoint as an Agent that needs user input and aggregate that red attention state at its conversation root and leaf pickers, ahead of Working, yellow New updates, and green Live. Keep it unresolved for transcript stabilization until the provider returns to working or idle. An idle transition triggers a fresh SDK transcript read; keep the live endpoint visually pending until the rebuilt graph is ready so a completed agent message and its following draft leaf appear atomically. Keep activity state ephemeral and informational: process exit remains authoritative, and detection must not control permissions or inject input.

Supplement Claude terminal observation with invocation-scoped `Stop` and `StopFailure` HTTP hooks injected through a hooks-only additive `--settings` argument. An authenticated loopback listener belongs to each acquired launch, admits only bounded main-session payloads, discards conversation text, and emits coalesced reconciliation hints without decisions or context. Preserve user hooks and managed restrictions; unavailable delivery falls back to terminal observation. Stop hooks run in parallel and another hook can continue generation, so a hint only requests fresh screen evidence, never directly marks idle or completes a turn. Listener cleanup is explicit, idempotent, and bounded below the supervisor's cleanup deadline, with scoped finalization as a backstop.

After Claude reports that a historical fork was created, retry bounded reads of its active transcript and copied-record provenance before validating correspondence. Create the provider fork only once and keep provenance and payload validation strict. Require the physical child to contain every source conversation record in order through the requested boundary, no records beyond it, and an exact source role and payload for each record. Claude's compaction reconstruction may omit records that the fork physically copied, so the active child transcript may be an ordered subsequence of the validated shared prefix; require it to reach the requested source and reject reordered, contradictory, or child-specific records within that prefix. If correspondence still cannot be validated, save no ancestry and refresh the created child as an independent root rather than guessing its relationship or deleting its provider transcript.

Claude compaction can also reconstruct a newer summary before older preserved records. Physical file order therefore proves copy integrity, but does not define conversation order. Validate every physical copied record, including inactive history and identical re-emissions, while saving shared message correspondence in validated navigation-history order. Repeated UUIDs must retain the same role and payload, and every copied occurrence must match its source position and explicit provenance with a consistent one-to-one identity mapping. A fork's active path may follow either the source SDK's compacted-context order or its validated navigation order; require one complete evidenced ordering, never a hybrid, and require it to reach the selected boundary. When a preserved message precedes its current compaction anchor, validate the SDK's read of the original physical prefix through that boundary. Every record in that prefix's active path must belong to the validated navigation prefix. Inactive physical records are not automatically graph ancestry: they may belong to history replaced by compaction.

Automatic terminal-return and completion refreshes reread the affected sessions and merge them with cached unrelated transcripts; targeted reads obtain only those sessions' metadata, without rediscovering the project. Initial loads and explicit manual refreshes remain complete snapshots. Initial loading publishes the catalogue first and then disjoint batches of transcript results; catalogue rows have explicitly pending history and unknown counts until their family is read. Entering an unread family starts a targeted read without waiting for unrelated hydration. The final initial snapshot must not reconcile already published reads twice or overwrite a newer targeted read. Only completion of the full catalogue operation establishes full-snapshot absence. Preserve every ordered activity transition reported in one PTY chunk. Because provider persistence can lag an idle title, retain the pending endpoint and retry with bounded backoff until the transcript advances to a provider-confirmed completed turn. If the session resumes working, reject the stale completion and keep newly persisted assistant-tail records behind the single working endpoint.

Accepting the current user prefix and completing the assistant response are separate transitions. After an observed rewind, validate replacement history against the retained prefix at the rewind boundary, not the discarded full transcript. Accept newly persisted user records while working, blocked, or waiting for completion, and place the pending Agent endpoint after them; withhold only the unfinished assistant tail. Advance the completion baseline with the accepted user prefix without clearing its completion wait or marking unread updates. Owner-local replacement evidence rejects lagging discarded message identities through prefix confirmation. Compaction's historical classification can update accepted records without changing their logical identity or proving a response completed.

A submission starts bounded, owner- and observation-revision-scoped discovery of its persisted user prefix independently of response-completion polling. Use the same short backoff schedule as completion, but a separate attempt budget. Return and manual reads may satisfy discovery without resetting its budget; successful lagging reads never manufacture a user node from terminal text. Stop discovery when a new persisted user is accepted, when another submission or undo supersedes it, or when the owner stops. Idle hands discovery to completion reconciliation, which can still accept a user prefix before the answer is available. Exhaustion ends discovery without inventing history or reporting a completion failure.

Idle does not guarantee a completed response: a user can cancel generation or undo the send. An observed, unsubmitted rewind clears the completion wait immediately and projects the restored prompt as a draft rather than sent history. A prompt restored after Escape may confirm this observation when it matches the tracked submission and the screen is idle; Escape alone is not evidence. That restored composer overrides a stale working title. A subsequent submission starts a new completion cycle. If bounded completion reads succeed without a completed turn, reconcile their provider history without inventing new updates or showing a completion error; unavailable reads still report failure.

Provider history is not append-only: an external rewind or missed composer observation can shorten or replace it. Without an observed rewind, retain the previous history on the first unexpected idle read and automatically confirm with another incremental read after 100 ms. Accept two matching reads; stop after three changing reads and report the instability. This is a consistency heuristic, not a provider revision guarantee. Failed reads or renewed activity discard the candidate. A shortened prefix alone never proves a new turn completed: preserve the completion barrier through its bounded retries, then reconcile the replacement without marking a new update. Rebuild the graph from accepted history while retaining independently copied descendant evidence.

Compaction is distinct from rewind. Claude's ordinary filesystem SDK read is authoritative for active context. Separately import session records to reconstruct navigation history; do not substitute an imported-store read for active context. The pinned SDK applies filesystem-specific precompaction handling, and real files with repeated compaction can produce different active records through these two APIs. A full snapshot gives each admitted transcript its own bounded read deadline, so time spent discovering sessions or waiting for a concurrency slot does not exhaust unread sessions' budgets. A compact boundary's explicit `logicalParentUuid` links to the history it summarized. Ask the SDK to read an in-memory navigation projection that follows those links instead of its compact-context rewiring; never write this projection to the provider store. The SDK still chooses the current path and reconstructs streamed blocks, so abandoned rewind paths are not resurrected. Validate that the navigation history contains the active context's exact identities, roles, and payloads, and reject missing or cyclic compaction links rather than silently truncating history. This reconstruction works on fresh startup without caching or persisting message content.

Navigation projection resolves effective transcript content with the pinned SDK's last-write-wins behavior and recognized record types, while retaining repeated versions as separate ancestry evidence. A preserved record's newest parent can describe compacted-context placement rather than historical parentage. Interpret `preservedMessages` and `preservedSegment` as explicit context transformations: recover historical parents from unambiguous local versions or matching ancestor versions reached through validated copy provenance, then reconnect postcompaction continuations in the same candidate projection. Ancestor identities are session-scoped and must be translated into evidenced copies in the current transcript before an edge is projected. Context-only preserved records retain their evidenced selected placement. When the SDK-selected continuation branches inside a preserved prefix, exclude the bypassed later preserved records instead of resurrecting the discarded tail. Older preservation metadata must not reapply a context edge to restored navigation records.

Follow parent identities through the logical ancestry required by the SDK-selected conversation. A parent appearing later in the file, or being re-emitted later, is not a cycle. Validate the candidate ancestry iteratively and detect actual cycles across ordinary and compaction links; report missing or ambiguous evidence rather than selecting an arbitrary old parent or cutting a loop. Unrelated or superseded boundaries do not invalidate the selected path. Ordinary dangling parents retain the SDK-supported truncated prefix; an explicit logical compaction link requires its referenced history. Canonicalization and parent changes apply only to the in-memory navigation projection; fork integrity validation consumes every original physical occurrence.

SDK forks can retain preservation metadata containing parent or ancestor UUIDs even though record UUIDs were remapped. One operation-local record-evidence index serves preservation references, historical parents, anchor association, and continuation evidence. Follow explicit `forkedFrom` lineage through matching record versions instead of using cross-session evidence only for UUID translation. A child with one context-parented version may still have a recoverable historical parent in an ancestor snapshot. Immediate copied-record aliases and sufficient local historical versions do not require the original parent file. Otherwise request only the required ancestor snapshots within the existing read deadline and reuse them throughout the projection. Resolve those source identities through the SDK's provider-wide UUID lookup: fork provenance does not imply that the source file is in the current project's directory. The foreground session catalogue remains project-scoped. Missing snapshots are acquisition requests, not evidence that no historical parent exists. Missing or contradictory evidence after acquisition fails the affected reconstruction without guessed aliases or provider mutations.

Copied-record matching checks meaningful payloads for each recognized record type. User and assistant messages retain exact message-payload checks; attachment, progress, and system records also compare their own data, excluding SDK-remapped envelope fields. Attachment links participate in ancestry and must not compare equal merely because both records lack a `message` field. When translating an ancestor parent, only SDK-omitted progress records may be traversed without a copied local identity. Traverse those chains iteratively, retaining all parent alternatives because omitted progress payloads cannot select a historical version. Reject cycles, conflicting alternatives, and unmapped message or attachment parents rather than converting them into an invented root. An explicit null ancestor parent remains a valid root.

Read the filesystem SDK context with system records included, retaining its last system record as an anchor while keeping those records out of displayed conversation messages. This identifies the selected compaction path even when its active user/agent context is empty. The SDK still reconstructs the projected history, including historical streamed siblings and tool results. Require that reconstruction to retain the system anchor and every active message's exact role and payload before accepting it; rewiring must never silently switch to a detached leaf. With no SDK-selected path, do not resurrect unrelated imported history.

Keep explicit compact summaries hidden in the normalized history; summary wording is not evidence. Mark pre-compaction records outside the active context as historical. Save validated fork correspondence in navigation-history order, independently of active-context ordering used for strict SDK fork validation. Forking a pre-compaction node validates against the SDK's read of the original records through that exact boundary. Existing relationships may omit historical records and order summaries before preserved messages; hidden boundaries and omitted historical prefixes must not invalidate their attachment. If an older provider record supplies no logical link, retain only independently validated shared history rather than guessing ancestry from physical order. Continuations attach to the last surviving shared node, falling back to the recorded source only when compaction omitted the entire shared prefix.

When a hidden live session reaches that provider-confirmed completion boundary, mark its Draft endpoint as having new updates and aggregate that state in the conversation-root picker. This state is ephemeral application UI state rather than provider or relationship metadata. Keep it while the session remains live, clearing it after the exact stock terminal is successfully shown or the live session is stopped or removed; navigator selection alone does not count as viewing the update.

Claude may persist one user turn as multiple assistant records, including streamed content blocks and continuations around tool calls. Normalize those raw records into one visible Agent node per user turn while retaining every UUID for prefix validation, removals, and provider operations. Internal task-notification user records are hidden and are not replayable user prompts, but start a distinct Agent display group for the response they trigger, including subagent and background-monitor results. Ordinary hidden tool results do not split a group. A newly selected grouped Agent forks from its latest represented raw boundary. An existing recorded fork closes the display group at its exact source so later parent content never appears before the branch.

An OSC Working title can arrive before its screen paint. Suppress an unchanged composer snapshot at that transition, but do not require a later OSC Idle title to accept every subsequent idle screen. A changed idle screen or a composer following an observed working footer triggers the normal bounded transcript-completion refresh. Unknown screens do not imply idle, and visible blockers and working footers retain priority.

Manual refresh resamples every running terminal before reading provider history. A two-second owner-local fallback probe also resamples non-idle terminals, including hidden ones; provider lifecycle hints request the same check. A suppressed unchanged idle screen requires two explicit samples 100 ms apart within one probe, not merely repeated render frames. Input, output, a changed screen, or a new probe invalidates the previous recovery candidate. Serialize probes per owner and reject stopped, disposed, or adopting owners before each sample. A complete bottom bordered Claude composer can establish idle with a hidden cursor without making its ordinary draft readable. These are consistency heuristics, not provider revision guarantees: elapsed time or an unknown screen never establishes idle. Publish recovered activity through the normal sequenced owner event stream and retain transcript completion barriers. Manual refresh reports unresolved Working observations and partial transcript-read failures instead of silently claiming resynchronization succeeded.

Terminal snapshots must compose pending VT output before reading both text and cursor: OpenTUI's default snapshot otherwise mixes last-painted text with the current cursor. Snapshot composition must not publish screen callbacks reentrantly; callers explicitly observe the composed snapshot before interpreting input. Normal render frames continue publishing screen observations. While waiting for a confirmed rewind's composer, a complete input box bounded by both horizontal rules can supply an approximate draft even when the hardware cursor is hidden; ordinary drafts still require cursor-local evidence, and blockers or working footers reject the fallback.

Composer and submission observations travel through the same owner-identified, sequenced event stream as activity and identity transitions. A positively empty composer clears the preview; an unreadable composer supplies no new evidence. The supervisor may cache presentation text but never owns rewind semantics. The application actor owns provisional rewind placement and the tracked replacement submission, so returning to the navigator cannot overwrite newer observations with a cached draft. Dialog cancellation and files-only restore do not establish a conversation rewind. Approximate prompt text may identify a provisional boundary only when unambiguous; provider history remains authoritative.

An unresolved rewind occurrence invalidates obsolete observations and completion work but does not invent a boundary. Complete restored composer rows may match a whole prompt with optional whitespace only at evidenced terminal row joins, since a soft wrap can split an identifier. Preserve within-row token separation; never use arbitrary substrings or whitespace deletion to establish identity. Partial, pasted-placeholder, elided, or duplicate targets remain unresolved.

Recovery of a missed or unresolved boundary must not depend on an assistant response. With an observed rewind, tracked submission, or pending completion, confirm a replacement user prefix through two matching provider reads, independently of changing assistant tails. Validate retained logical identities and payloads, reject reordered or mutated retained records, rebase submission discovery to the confirmed common prefix, and withhold only the pending assistant tail. A shortened prefix alone does not prove a submission or completion. Active replacement prefix constraints end at provider-confirmed completion, exhausted completion reconciliation, or accepted idle cancellation history without a pending submission. Retain discarded-identity protection while allowing a later independently confirmed rewind to an earlier prefix. Late responses after exhaustion reconcile as history without manufacturing unread-completion notifications.

Transcript reconciliation decides accepted history, completion, and provisional-anchor invalidation together. A rejected incoming transcript cannot invalidate the anchor filtering the retained history. Each read captures session-local observation revisions together with immutable terminal owner IDs; a newer submission, unsubmitted rewind, or changed owner invalidates that session's in-flight result and schedules a fresh incremental reconciliation without discarding unrelated results. Obsolete failures also request a fresh read rather than ending reconciliation or advancing a newer completion's retries. Observed rewinds request reconciliation even when no activity transition occurs. Once accepted provider history confirms the shortened path, discard the provisional anchor; independently copied descendant history remains intact. Completion consumes a submitted preview even when the composer cannot be read. A repeated undo of a tracked replacement can preserve its already established boundary before the replacement reaches provider reads. These observations and provisional state are process-local and never persisted as conversation content.

Graph construction does not interpret rewind. Current session paths determine endpoint placement independently of retained fork ancestry: given the same accepted provider history and validated relationships, settled placement is identical whether or not this process witnessed the rewind. Explicit empty history places an endpoint at the family origin; missing or unread fork history retains its recorded source until a read succeeds. Compaction omission uses its explicit history evidence, not a blanket fallback for every shortened transcript. Hidden tails resolve to the last materialized node. Materialize a distinct leaf when an endpoint lands in shared ancestry. Leaf-picker distances and destinations follow current placement, preserving an open picker and its selected session when its source survives a topology change.

## Codex Forks Only At Completed Turn Boundaries

Codex app-server forks whole turns rather than arbitrary transcript items. A valid Codex fork target is therefore the final agent item in a completed turn. User-message replay, system-item targets, intra-turn targets, and incomplete turns fail before creating a child. After a fork, compare the copied child prefix against the source payloads and fail closed if Codex did not preserve it exactly.

Codex terminal activity and draft previews are observed conservatively from its OSC title and visible composer. An action-required title or recognized confirmation prompt is blocked rather than being mistaken for working or completion, because the user must return to the stock TUI to resolve it.

Codex titles cannot permanently veto newer screen evidence. Recognize structurally distinct spinner and action-required fields, including configurable spinner placement, rather than word-only statuses that collide with project or thread names. Removing a recognized activity indicator from the otherwise identical title can indicate idle; arbitrary unknown titles cannot. Current working footers and blockers take priority over the composer. Both providers use the same owner-scoped recovery mechanism. Codex's mutable `turnComplete` metadata is not logical message identity: completing a turn must not invalidate its accepted user prefix. Exact transcript stability comparisons still include that metadata.

## Graph Navigation Preserves Cursor Intent

Vertical navigation follows visible graph edges: up selects the parent and down selects a child. It never falls diagonally into a neighboring branch. Horizontal navigation uses the same world-space node layout as rendering and may cross branches, root chains, and viewport boundaries.

Navigation retains a preferred world-space column for vertical movement and depth for horizontal movement, plus the exact source of the latest transition. This mirrors a text-editor cursor: moving through an ambiguous parent or a shorter neighboring branch and then reversing returns to the node that was left. Blocked movement does not discard that intent. Rebuilding or resizing the graph resets it. The synthetic family origin does not participate in navigation.

Persist navigation using opaque session IDs and message aliases, never list indexes or generated graph node IDs. Scope every lookup to the current application-instance ID. If a runtime is reconstructed with that same ID, restore its surviving roots selection or graph target; if it recorded a terminal view, ask the provider to resume that session and fall back to its graph or the roots list when it is unavailable. A fresh process uses a fresh instance ID and starts from the default view. Persisted navigation identifies semantic provider state only. PTYs, emulator scrollback, modal state, and approximate drafts remain process-local.

## One Application Actor In One Foreground Process

Each invocation has one application-state actor. User input, terminal callbacks, command completions, refresh results, and shutdown state changes enter its ordered event queue; only the reducer executed by that actor may replace `ApplicationState`. Effects may run concurrently outside the actor, but they return immutable completion events instead of mutating application state directly. Terminal callbacks are serialized before dispatch and carry immutable owner IDs and sequence IDs so stale activity, exit, or identity events can be rejected deterministically.

Command completion delivery is an exit finalizer, including interruption, so a cancelled provider operation cannot strand its caller. Presentation actions run in isolated scoped fibers while retaining foreground ordering. Refresh and quit use a separate background lane: provider reads must not block navigation against the last accepted snapshot, and quitting must not queue behind a stalled fork or terminal launch. Foreground mutations still guard conflicting input. Compatible incremental reads may share already-running reconciliation when its captured observation revisions remain current.

Cursor requests complete when the actor accepts them, not when their navigation record reaches disk. The navigation writer retains one in-flight save and one latest pending destination. Scheduled cursor saves have a 200 ms batching window; new input replaces the pending destination without extending that window indefinitely. Durable writes and explicit flushes bypass the delay. Asynchronous save failures remain visible and shutdown flushes the latest accepted destination. Presentation retains only the current selection request and latest queued replacement. Each request carries an acknowledgment identity so an older publication of the same node cannot acknowledge a newer cursor movement. Open and fork capture the semantic target selected at input time.

Production cursor saves execute in a scoped worker thread so parsing, validating, canonicalizing, and serializing the unified provider-state document cannot occupy the input/rendering thread. Send typed navigation requests, never state-transform closures or stale copies of the complete document. The worker uses the foreground invocation's instance ID and the same cross-process transaction lock, and attaches to already initialized state without recreating a lost document. Saves preserve shared relationships, owners, identity journals, and other invocations' navigation. Shutdown asks the worker to drain admitted transactions; terminate it only after its drained acknowledgment and await exit. A close timeout reports failure and unreferences the worker instead of killing a thread that may hold a transaction lock. Worker failures settle pending callers and prohibit new saves. Explicit runtime shutdown includes worker close failures, with scoped close as a backstop.

Projection partitions sessions by recorded relationship connectivity, including missing parents and invalid attachments, and runs complete graph validation within each component. Reuse unchanged family graphs across unrelated transcript updates; retain equal accepted transcript and session references. Terminal activity alone does not invalidate graph topology. Cache layout separately from status and cursor selection, cache root summaries, and lazily resolve endpoint choices only when consumed. Caches contain derived, invocation-local data and never become persisted conversation truth.

During initial hydration, stage independent transcript results until each recorded family has a read outcome for every required member or already accepted local history. Publish the family coherently, rather than exposing a child as an independent root while its parent is still loading. Read outcomes are separate from retained accepted history: Pending, Ready (including verified empty history), Unavailable, and Missing are explicit process-local states. A failed or missing read retains the last accepted graph where available. Otherwise the discovered family stays in the catalogue with its failure reason and a targeted Enter-to-retry action. Successful retry clears that failure. Complete snapshots that omit a discovered session's read report an unavailable history, not an indefinitely pending row. Known empty inactive families and validated navigator removals remain hidden; neither read failure nor loading completion proves discovery absence. The first completed family is never a selection request. Preserve cursor identity through loading, failure, and family reconciliation.

Graph rendering queries a selection-independent geometry index and clips connector segments before rasterization. Off-screen message content is never formatted for a frame and canvas allocation is bounded by the terminal viewport. Root selection is separate from the immutable ordered root collection: retain row data, session indexes, aggregate working state, and column measurements across cursor-only publications. Cache prepared visible root text and selected/unselected styles by row identity and viewport measurements. Selection acknowledgments that do not change visible state do not prepare another frame.

Presentation invalidations coalesce at OpenTUI's pre-render frame callback, rather than a separate zero-delay timer. Production rendering targets 60 FPS with a matching maximum; prepare the latest dirty view once before native composition and unregister the callback during teardown. Navigation reuses geometry rather than reconstructing it for every keypress. A validated fork returns its already-read child history for immediate local projection before terminal activation; unrelated refreshes are not part of that critical path.

This actor boundary is not a daemon. Provider PTYs and all runtime scopes still belong to the foreground process, and separate invocations have separate actors even though they coordinate durable provider state through the transaction lock.

Live PTYs belong to the foreground `claude-tree` process. Closing the application gracefully terminates its child agent processes and restores the host terminal. Persisted sessions can be resumed on the next launch.

Terminal launch resources have explicit provider cleanup in addition to scope finalization. A prepared launch acquires its provider sidecars, proxies, subscriptions, and capability files together and returns an idempotent close effect. Stopping or rollback invokes that close effect with bounded retries, then closes its provider scope. Scope finalizers are a backstop, not the primary ownership protocol. Do not release a persisted terminal owner until its process group is absent, provider cleanup and scope closure are confirmed, any identity adoption is settled, its PTY is closed, and the child has been detached with `unref`.

Shutdown releases the navigator and terminal emulators immediately, then remains in the foreground for a short, bounded cleanup of each owned agent process group. Keep PTYs open during the graceful termination window so the agent can finish its signal handling; escalate surviving process groups from `SIGTERM` to `SIGKILL`, verify absence, close their provider resources and PTYs, and detach them before the application exits. Unknown or failed verification is a cleanup failure, not successful shutdown.

Stopping one live endpoint uses the same bounded process-group cleanup but leaves every unrelated endpoint running. Mark the session as stopping and reserve its session ID before signaling it, so graph actions cannot start a second owner while cleanup is in progress. Keep that ownership reserved if cleanup cannot be proven complete; application shutdown is the final cleanup boundary.

Before persisting a navigator removal, stop every affected live session with this same bounded cleanup. Do not apply the removal while an affected session remains live.

After an intentional stop, rebuild the graph from a fresh provider transcript read. A Draft with no persisted message disappears. A recorded fork's copied-prefix status is ancestry evidence, not by itself a reason to draw an extra Fork leaf. Materialize stopped copied-only endpoints at the empty-history origin or where competing endpoints or message continuations require distinct leaves. If a message's sole surviving child is that stopped endpoint, collapse it onto the message for layout and navigation while retaining the domain endpoint and resume identity. This also applies when a parent rewinds away from history retained only by its child. Recompute materialization and Fork numbering from surviving topology after removals; live endpoints remain visible. A working response is frozen only to the extent the provider persisted it, and later resume creates a fresh Draft after that persisted boundary. Never reconstruct or append transcript history from terminal emulator cells.

A daemon/client split is intentionally deferred. Add one only if surviving application exit becomes a real requirement; do not pay the lifecycle and IPC complexity merely to imitate a terminal multiplexer.

Do not run two live processes against the same provider session ID, because concurrent transcript ownership is unsafe. Different branches may run concurrently.

Shutdown is an idempotent direct lifecycle operation, not merely an event queued behind ordinary work. The presentation, signal path, and scope finalizer call the application runtime's shutdown API directly. It stops admission of new terminal work, flushes pending navigation, asks the terminal supervisor to clean every owner concurrently, and reports success only after verified cleanup. Scope interruption and process exit remain last-resort backstops; they must not be the normal way provider resources or leases are released.

## Herdr Integration Reports One Visible Agent

When Herdr supplies its pane environment, report activity through the Herdr CLI with a dedicated `custom:claude-tree-lifecycle` source. Reporting is optional, serialized, bounded, and non-fatal. Reassert state shortly after each transition, including once after Herdr's release reacquisition window, so rapid restarts, startup process-detection races, and transient command failures recover. Send a low-frequency heartbeat at one exact interval per cycle so a Herdr server restart does not permanently lose registration. A timed-out Herdr child receives bounded `SIGTERM` and `SIGKILL` exit-verification windows and is then detached with `unref`. Release the source during shutdown. Do not add a runtime dependency on Herdr.

Register the pane's agent as `claude-tree`, which is the foreground application Herdr actually hosts. Application view publication is the production reporting authority: while viewing a tree, report the same aggregate status as that tree's root-list row; while viewing a stock terminal, report only that session; while viewing the roots list, report idle. Unrelated trees must not override the displayed tree or terminal. Herdr's CLI accepts idle, working, blocked, and unknown: map Live and New updates to idle with descriptive messages, Working to working, and Needs user to blocked. Remove Herdr's pane-specific environment variables from nested provider processes so their own hooks cannot claim the outer pane or persist a provider identity there.

Use one status priority and one marker renderer across session endpoints, root-list rows, and both Open leaf and Jump to Leaf pickers: Needs user (red dot), Working (animated braille), New updates (yellow dot), Live (green dot), then inactive (muted hollow dot). Working outranks unread updates, including when an unread session starts another turn; merely navigating the tree does not mark a terminal as viewed. Live requires a terminal, not just a persisted session. Open pickers refresh their status markers without resetting selection, and root-list working indicators animate independently of provider refreshes.

Herdr reporting does not change process ownership. claude-tree continues to own every provider PTY, and Herdr does not receive terminal handles or act as a multipane runtime. Navigation recovery remains scoped to the current application instance; a new invocation cannot restore a prior PTY or emulator state.

## Input And View Ownership

The application has two modes: navigator and embedded terminal. In terminal mode, input belongs to the selected agent except for one configurable host escape chord. The initial default is `Ctrl+Space`, selected explicitly for returning to the navigator.

Avoid intercepting ordinary agent keys. Host shortcuts should be mode-specific, visible to the user, and configurable when practical.

## Shared Working Tree Is Deliberate

Every agent process starts in the same project directory. This allows branches to observe and build on the same filesystem state, but it also permits simultaneous edits and conflicts. The application should communicate status accurately and must not claim branch-level file isolation or silently create worktrees.

Future agents have latitude in UI composition, state modeling, testing strategy, and dependency choices. Changes should be judged against the goals in `project-goals.md` and the behavioral constraints above.
