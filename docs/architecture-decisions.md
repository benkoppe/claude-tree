# Architecture Decisions

This document records decisions that shape the project and the reasons behind them. Specific libraries and versions are an initial baseline and can be upgraded or replaced when a better implementation preserves these constraints.

## Providers Are Explicit Application Dependencies

One provider is selected when the application starts and is injected into the application controller. The provider owns session discovery, transcript normalization, new and resumed session launch preparation, historical branch semantics, and interpretation of provider-specific terminal output. The application core owns graph construction, navigation, rendering, process lifecycle, and relationship persistence.

Session and message identifiers are opaque provider strings. The core must not assume UUIDs, provider CLI flags, transcript payload formats, or a particular branching implementation. Historical branch results expose validated parent-to-child message correspondence so the graph can merge shared history without understanding how the provider created it.

Branching is an explicit capability. A provider that cannot branch through a supported interface must report that limitation rather than editing transcripts or simulating fragile terminal input. Claude Code and Codex are shipped providers, and only one provider's sessions appear in a given application invocation.

## Stock Agent TUIs Run In Owned PTYs

Each live branch is a normal interactive provider process attached to its own pseudo-terminal and terminal emulator state. The application forwards input to the selected process and continues consuming output from every hidden process. Keep hidden emulators transparently composed beneath the navigator so provider-specific screen observers continue receiving updates without exposing another terminal surface.

Only the selected emulator is rendered. Switching views must not suspend or recreate unrelated agent processes.

Every in-memory terminal owner receives an immutable owner ID before acquisition begins. That ID, rather than the provider session ID, identifies the resource bundle and every asynchronous callback for its lifetime. Session IDs may move during provider-native identity adoption; owner IDs never do. Sequence terminal events as well so a delayed callback from an earlier state cannot mutate a replacement owner that happens to use the same session ID.

Opening a terminal acquires an advisory OS session guard, provider resources in a dedicated scope, and the emulator and PTY before focus. Roll back when any stage fails. Incomplete cleanup remains process-local and blocks a replacement in this invocation; no terminal ownership, resource inventory, or crash journal is persisted.

On Linux and macOS, advisory guards use application-held `flock` descriptors. An admission lock serializes discovery and creation of independently locked claims per session. An explicit override acquires its own claim without releasing another invocation's claim; later opens still warn while either invocation remains active. OS locks release on application death. Empty leftover files are not ownership evidence. Codex capability files use private temporary directories with ordinary scoped cleanup. Detached providers can survive an abrupt crash; the application does not inspect or recover them.

Session guards receive an explicit root at `$XDG_STATE_HOME/claude-tree/session-guards`, separate from database and project paths. Provider and opaque session identity define the namespace. Failed or interrupted acquisition closes admission and rolls back any newly created claim, including failures in admission cleanup. Release is idempotent and retries incomplete close or unlink steps without treating failed cleanup as success. While holding admission, discard only recognized claim files proven unlocked; preserve live claims, unrelated files, the admission inode, and session directories so concurrent invocations cannot split the lock namespace.

This preserves the complete stock-agent experience and avoids maintaining a partial clone of its UI. It also rules out tmux and Herdr-style visible panes as the primary architecture.

The generic terminal manager executes provider-prepared commands and delegates activity and draft observation to a provider-created terminal observer. The initial implementation uses Bun's native PTY API with OpenTUI's `EmbeddedTerminalRenderable`, which uses Ghostty's VT parser. This combination has been validated in the development environment, but the ownership model is more important than those particular dependencies.

Serialize launch admission by session identity using the adapted keyed executor. Stop captures the immutable owner or pending launch and cancels before waiting for that exact launch, never its replacement. Acquisition stays outside the shared publication gate so unrelated terminals remain usable. Track rollback through shutdown. Semantic events wait for registration and activation; activating an existing terminal revalidates its identity.

Identity adoption reserves its destination in memory and acquires its guard before committing metadata and publishing to the actor. Owner-local serialization prevents identity mutations from racing cleanup. Conflicting owners or admitted launches in this invocation fail closed. Shutdown releases surfaces promptly and cleans owners alongside acquisition rollback, including owners registered while draining.

The Codex adapter validates consumed protocol fields and preserves dispatch, unsent-cancellation, and cleanup evidence. Its transparent TUI proxy forwards ordinary frames immediately; only frames waiting behind an identity acknowledgment enter the bounded ordered queue. Normal MCP bootstrap traffic must not exhaust that queue without an identity barrier. Preserve the first termination cause and native close details so local rejection is distinguishable from server death. The adapted keyed executor retains its MIT notice in `THIRD_PARTY_LICENSES`.

## Provider APIs Are Session Tools, Not The Chat Runtime

Use supported provider APIs for session discovery, message reads, and historical forks. For the Claude adapter, historical branching is based on `forkSession(sessionId, { upToMessageId })` rather than direct transcript manipulation. For Codex, short-lived `codex app-server --stdio` processes perform thread listing, reading, and forking; interactive work remains in the stock TUI connected to its owned loopback sidecar and transparent proxy.

The packaged SDK and CLI baseline is `@anthropic-ai/claude-agent-sdk` 0.3.251 with Claude Code 2.1.251. Upgrade the pinned SDK deliberately and verify session compatibility. Do not version-gate an externally installed Claude Code executable: metadata reads and historical forks use the pinned SDK, and every created fork must pass strict copied-prefix validation before its ancestry is saved. For Claude forks, validate each copied record through the SDK-imported child's explicit `forkedFrom` provenance and exact payload rather than assuming the SDK's reconstructed active transcript has the same length. If a changed transcript format prevents that validation, preserve the created child as an independent session rather than guessing its relationship.

The packaged and validated Codex baseline is 0.150.1. Do not version-gate an externally installed Codex executable: app-server responses are strictly validated, unsupported protocol changes fail the affected operation, and every historical fork must preserve its copied prefix exactly before ancestry is saved. One refresh batches all transcript reads through one app-server process, and every metadata operation closes its process with timed signal escalation followed by confirmed resource finalization.

Distinguish ordinary request failure from mutation ambiguity. A provider mutation may have committed once its request was sent even if its response times out, the transport closes, or the returned child identity is invalid. Never retry such a mutation automatically. Return an explicit ambiguous outcome, perform a full provider snapshot reconciliation, and do not invent ancestry or launch a guessed child. Reads and requests proven not to have been sent may still use bounded retries. This rule applies to both Claude `forkSession` and Codex `thread/fork`.

Once a trustworthy child identity is returned, publish it immediately as a local session with an explicitly provisional requested origin, and start ordinary terminal admission without waiting for copied-history verification. Retain a provider-owned, process-local verification receipt containing captured source evidence and the prepared launch, including replay prefill. Provisional graph placement never supplies shared-message aliases or persisted ancestry: materialize the child's own path separately. Subsequent cancellation, read failure, or observation expiry cannot turn that known child back into mutation ambiguity. Compatible missing or incomplete copy evidence remains pending, with capped-backoff read-only polling and no default total attempt or work deadline. Unsupported reads and general read failures stop automatic polling as unavailable and retain provisional placement; contradictory copied payload, ordering, or provenance detaches the child into an independent root without stopping its terminal. Neither permits ancestry persistence. Explicit validation budgets stop observation as unverified rather than invalid. Native Claude fork Promises cannot be cancelled: retain their settlement through interruption and timeout finalization, publish late confirmed identities without taking newer focus, and never repeat the mutation. Codex records actual native dispatch separately from queued/unsent cancellation.

Verification is quiet background work, not a foreground operation or dedicated keybinding. The navigator labels provisional placement and retains non-blocking issue details through `e details`; manual Refresh retries unavailable verification without repeating the mutation. Receipts never enter SQLite or a read worker; retries use the captured source, not a newly read parent. Opening or continuing the child preserves its receipt. Verification completion never launches a terminal or changes focus, and never replaces newer accepted history with its captured read. Save verified ancestry before atomically promoting provisional placement into a shared-history branch. Metadata-write failure retains verified evidence for metadata-only retry. A zero-prefix Claude replay has not created a provider transcript yet: after metadata-only retry, keep its lazy prepared launch until explicit Open, with the ordinary transient-launch rollback. Do not attempt to resume that unstarted identity. Navigator removal retires affected verification. Shutdown cancels observations and awaits native command settlement before closing persistence. A later invocation has no receipt or provisional placement: unresolved children appear independently, and missing ancestry is never guessed from content.

Reply ownership follows an actor-owned command phase. Before handoff, creation owns the user's fork reply; at confirmed-child handoff, terminal admission becomes its sole owner and the creation command becomes reply-free background verification. Verification success, failure, supersession, and shutdown cannot settle that launch reply. Resolve queued completions against the current actor-owned phase, including defect recovery, because a provider completion may have queued before handoff was processed. Foreground operation status lasts until terminal admission settles, independently of verification.

Construct families by traversing explicitly distinct verified and provisional attachment edges, not by grafting an already built child family onto the provisional source. Provisional attachment materializes only the child's own path without shared aliases; verified descendants retain the existing correspondence and endpoint rules, including zero-prefix placement at the family's synthetic origin. Shared-path reconstruction uses the session's visual entry point when a verified descendant restores omitted prefix nodes inside a provisional path. Label provisional entry edges after that reconstruction, without relabeling verified origin descendants. Promotion and detachment preserve semantic selection and repair a running descendant's return destination without moving terminal focus.

Retiring fork verification follows semantic navigator removal, not the list of terminals to stop. Compare the existing forest with the same forest projected through the requested removal: a surviving parent message remains a valid source even when its endpoint or later tail is removed. A receipt awaiting Refresh is subject to the same rule as an active observation. Retire evidence when removal discards the child endpoint or actual source; retain native mutation settlement for a creation whose requested source was removed.

The projected forest defines settled navigator family membership, including independent fallback when a provisional source is absent. Catalogue families supply placeholders while initial discovery is pending, but cannot hide an already projected local or live graph. Root rows, activation, selection repair, and workspace navigation use that same navigation-family projection. A rewind that prevents provisional attachment does not discard verification evidence: the child stays independently selectable, and restored source history can support provisional placement again.

Codex does not allocate or persist a new thread until its first user turn, so a fresh thread cannot be handed to `codex resume`. New Codex sessions launch the stock TUI against a dedicated authenticated loopback app-server and let the TUI call `thread/start` when the user submits that turn. The application initially owns that terminal under a temporary ID, then adopts the real ID through the proxy's acknowledged identity transition. The terminal manager cleans up the sidecar with the TUI. Persisted sessions use short-lived metadata reads for discovery and the same observed remote TUI path for later resume.

Locally prepared sessions are an immediate overlay on the last provider snapshot. Project them into the conversation forest and establish their navigator destination before activating their terminal, including when the provider has not persisted or discovered them yet. Returning from a terminal must reveal that local graph synchronously; provider refresh reconciles metadata and transcripts afterward rather than deciding which navigator view appears. Temporary-to-provider ID adoption updates terminal ownership and the local graph projection as one transition.

Identity adoption is forward-only because the provider has already changed identity before the application observes it. Atomically replace relationships, removals, and per-instance navigation references for a temporary identity and save any validated relation. A native fork preserves source metadata and moves only this invocation's navigation. Then update the runtime identity and notify the actor, acknowledging the provider after projection. Failure stops the terminal rather than renaming the provider backward. There is no persisted acknowledgment journal or startup replay.

Forked sessions do not include the source session's file-history snapshots. A historical conversation fork therefore does not provide historical file rewind. Because all branches share the current working tree, it also does not restore files to their state at the selected message.

## Relationships And Navigator State Need Application Metadata

Claude sessions are persisted independently. Historical forking remaps message UUIDs and does not retain enough source-branch information for this application to reconstruct a reliable cross-session tree later.

Store only the missing relationship data: the child session, parent session, source message, and validated correspondence between shared parent and child messages. Treat that correspondence as retained evidence in both directions when a later compaction omits mapped records, and reconcile restored logical paths transactionally so contradictory metadata cannot partially mutate a family graph. Persist navigator-removal and current-view records as application-owned UI state. Keep them outside the repository in `$XDG_STATE_HOME/claude-tree/state.sqlite`, scoped by stable project identity and provider.

SQLite owns metadata transaction serialization and crash consistency. Use Bun's native driver with Drizzle, STRICT normalized tables, scoped foreign keys, WAL, and FULL synchronization. Projects have immutable IDs and mutable canonical directory associations. Session references have immutable local IDs and opaque provider session IDs; temporary identity adoption changes the latter without replacing references. Mapping ordinals preserve validated navigation-history order. No message-content table, process reservation, activity cache, or recovery journal exists.

Recognized SQLite schemas upgrade through reviewed forward migrations, with a consistent pre-upgrade backup and an exclusive OS-held schema gate. Live persistence clients hold shared gate descriptors, so migration never changes the schema underneath another invocation. Reject unknown newer schemas, contradictory migration history, and corrupt state in place. Legacy JSON schema v3 is accepted only through `state import-json`; retain canonical and semantic validation, reject older ownership/recovery documents and separate lease layouts, and leave original files untouched. Legacy processes must exit before cutover. Do not silently switch to an empty scope while unimported legacy metadata exists.

Relationships and removals are shared by all invocations for the same project and provider. Navigation is not: each foreground process receives an application-instance ID and may read or replace only its own navigation record. Concurrent invocations must not move each other's cursor, selected family, or terminal-return destination. A new process does not silently adopt another instance's navigation record.

Apply navigator removals after constructing the complete graph so relationship and message-alias resolution still use intact provider history. Prune only the selected tree or the selected node and its visual descendants from the navigator. Never edit or delete provider transcripts to implement removal.

Every surviving message leaf retains an opening destination after pruning. If removal discarded its provider endpoint, project a lazy continuation collapsed onto that leaf rather than resuming the original session's hidden tail. Enter from the leaf or any ancestor resolves this destination through the ordinary leaf picker. Only explicit Open creates a provider fork, using the existing provider-specific historical boundary semantics and strict ancestry validation; unsupported boundaries fail before mutation. Persist a continuation message anchor alongside the validated branch relationship so subsequent Opens, including after restart, reuse that child. This application-owned anchor is separate from the actual fork source and copied-message correspondence: user-message replay must not invent copied-user history. Removing the bound child or rewinding its current path before its copied fork boundary makes a surviving leaf lazy again; zero-prefix replays remain anchored at the family origin. Serialize continuation admission in the actor, retain its key through read-only verification retries, and never automatically repeat an ambiguous mutation. Open choices deduplicate real session identities while Jump to Leaf retains distinct visible destinations.

Sessions and forks not created or recorded by `claude-tree` should still be usable. When their ancestry cannot be established reliably, show them as independent roots rather than guessing from message content.

An explicit Open or Resume of a known persisted session does not require a successful cached history read. A missing-history observation is not a terminal admission decision: let the provider attempt resume through normal identity and ownership checks, and report an actual launch failure. Do not require a preliminary refresh or invent readable history; graph activation and historical branching retain their history requirements.

## Claude User Messages Replay From The Previous Agent

Forking an agent message copies the transcript through that exact SDK message. Forking a user message has different semantics: copy through its nearest earlier agent, then open the child with the selected user text in Claude's composer without submitting it. Transcript order is authoritative, and adjacent messages may have the same role.

A user replay with no agent ancestor copies a zero-message prefix but remains in the same conversation family. The graph represents all top-level roots as children of one synthetic empty-history origin. That origin is application state rather than a Claude message or session: it is never rendered, selected, counted, or used as a fork target, and no connectors are drawn from it.

User replay initializes the stock Claude composer through `--prefill` rather than timing simulated PTY keystrokes. Prompts that cannot be represented as text fail closed rather than silently losing content.

Claude Code does not expose semantic composer state. The application may show a conservative, in-memory preview parsed from the visible input box when leaving a live terminal, but it must mark that preview as approximate and never persist it as transcript or relationship state.

Observe both stages of Claude's native rewind dialog: message selection and restore confirmation. The visible dialog supersedes any provisional cancelled-send or earlier rewind target, including when opened through a provider shortcut rather than a typed command. Preserve the pending restore across confirmation-screen redraws after Enter; otherwise the restored composer is missed until the next submission. Escape cancels that pending observation. Only capture the restored composer after leaving the dialog; dialog selections are not submitted prompts. Recognize the pinned CLI's separate Rewind heading and restore instructions, including bordered and wrapped confirmation screens.

Claude's native restore can change only its in-memory path until a new transcript record is appended. Repeated SDK reads of the old path cannot resolve that live boundary. Observe conversation-restore occurrence separately from the restored composer and target resolution: emit one sequenced Rewind observation after a confirmed restore exits its dialog, even if the composer is empty or unreadable. Distinguish one-stage restore-and-fork message selection from two-stage restore confirmation; the word "fork" in that dialog is not evidence of a new persisted session identity. Interpret restore actions only in the confirmation stage, never from historical prompt text. Exclude complete composer boxes from dialog recognition.

Claude Code also does not expose semantic generation state to its terminal host. Observe its OSC terminal-title activity indicator directly from PTY output so hidden processes remain observable, with conservative matching against the last visible Claude screen as a fallback. Claude versions that pin an idle title under terminal multiplexers may still be working; a live bottom-screen working footer overrides that stale title, while a visible composer remains idle. Recognized permission and input prompts are blocked rather than working. Render a blocked live endpoint as an Agent that needs user input and aggregate that red attention state at its conversation root and leaf pickers, ahead of Working, yellow New updates, and green Live. Keep it unresolved for transcript stabilization until the provider returns to working or idle. An idle transition triggers a fresh SDK transcript read; keep the live endpoint visually pending until the rebuilt graph is ready so a completed agent message and its following draft leaf appear atomically. Keep activity state ephemeral and informational: process exit remains authoritative, and detection must not control permissions or inject input.

Supplement Claude terminal observation with invocation-scoped `Stop` and `StopFailure` HTTP hooks injected through a hooks-only additive `--settings` argument. An authenticated loopback listener belongs to each acquired launch, admits only bounded main-session payloads, discards conversation text, and emits coalesced reconciliation hints without decisions or context. Preserve user hooks and managed restrictions; unavailable delivery falls back to terminal observation. Stop hooks run in parallel and another hook can continue generation, so a hint only requests fresh screen evidence, never directly marks idle or completes a turn. Listener cleanup is explicit, idempotent, and awaits native server closure, with scoped finalization as a backstop.

After Claude reports that a historical fork was created, read its active transcript and copied-record provenance to validate correspondence independently of terminal admission. Small read batches preserve bounded retry of ordinary read failures; compatible incomplete batches feed the visibility loop rather than exhausting a total verification-attempt limit. A finite injected validation budget spans those pending reads, not a fresh budget for every batch. Create the provider fork only once and keep provenance and payload validation strict. Require every copied source conversation record in order through the requested boundary, with exact role, payload, and provenance. No new copied identity may extend beyond that boundary; identical evidenced re-emissions and child-native continuation records are distinct from excess original copy. Validate observed copied records even when the child is short: a missing suffix cannot mask a contradiction. Before child-native continuation, the active child may be an ordered subsequence of the validated shared prefix and must reach the source. After continuation, complete physical copy evidence can prove ancestry even when a child rewind or compaction changes its active path. If correspondence cannot be validated, save no ancestry and retain explicitly provisional placement unless evidence contradicts the attachment. Never guess a relationship or delete the provider transcript.

Claude compaction can also reconstruct a newer summary before older preserved records. Physical file order therefore proves copy integrity, but does not define conversation order. Validate every physical copied record, including inactive history and identical re-emissions, while saving shared message correspondence in validated navigation-history order. Repeated UUIDs must retain the same role and payload, and every copied occurrence must match its source position and explicit provenance with a consistent one-to-one identity mapping. A fork's active path may follow either the source SDK's compacted-context order or its validated navigation order; require one complete evidenced ordering, never a hybrid, and require it to reach the selected boundary. When a preserved message precedes its current compaction anchor, validate the SDK's read of the original physical prefix through that boundary. Every record in that prefix's active path must belong to the validated navigation prefix. Inactive physical records are not automatically graph ancestry: they may belong to history replaced by compaction.

Automatic terminal-return and completion refreshes reread the affected sessions and merge them with cached unrelated transcripts; targeted reads obtain only those sessions' metadata, without rediscovering the project. Initial loads and explicit manual refreshes remain complete snapshots. Initial loading publishes the catalogue first and then disjoint batches of transcript results; catalogue rows have explicitly pending history and unknown counts until their family is read. Loading families remain selectable but cannot be activated: show animated braille with `Loading`, ignore presentation activation, and reject actor admission promptly without starting another read or reserving a future open. Ready families open without waiting for unrelated hydration. The final initial snapshot must not reconcile already published reads twice or overwrite a newer targeted read. Only completion of the full catalogue operation establishes full-snapshot absence. Preserve every ordered activity transition reported in one PTY chunk. Because provider persistence can lag an idle title, retain the pending endpoint and retry with bounded backoff until the transcript advances to a provider-confirmed completed turn. If the session resumes working, reject the stale completion and keep newly persisted assistant-tail records behind the single working endpoint.

Accepting the current user prefix and completing the assistant response are separate transitions. After an observed rewind, validate replacement history against the retained prefix at the rewind boundary, not the discarded full transcript. Accept newly persisted user records while working, blocked, or waiting for completion, and place the pending Agent endpoint after them; withhold only the unfinished assistant tail. Advance the completion baseline with the accepted user prefix without clearing its completion wait or marking unread updates. Owner-local replacement evidence rejects lagging discarded message identities through prefix confirmation. Compaction's historical classification can update accepted records without changing their logical identity or proving a response completed.

A submission starts bounded, owner- and observation-revision-scoped discovery of its persisted user prefix independently of response-completion polling. Use the same short backoff schedule as completion, but a separate attempt budget. Return and manual reads may satisfy discovery without resetting its budget; successful lagging reads never manufacture a user node from terminal text. Stop discovery when a new persisted user is accepted, when another submission or undo supersedes it, or when the owner stops. Idle hands discovery to completion reconciliation, which can still accept a user prefix before the answer is available. Exhaustion ends discovery without inventing history or reporting a completion failure.

Idle does not guarantee a completed response: a user can cancel generation or undo the send. An observed, unsubmitted rewind clears the completion wait immediately and projects the restored prompt as a draft rather than sent history. A prompt restored after Escape may confirm this observation when it matches the tracked submission and the screen is idle; Escape alone is not evidence. That restored composer overrides a stale working title. A subsequent submission starts a new completion cycle. If bounded completion reads succeed without a completed turn, reconcile their provider history without inventing new updates or showing a completion error; unavailable reads still report failure.

Provider history is not append-only: an external rewind or missed composer observation can shorten or replace it. Without an observed rewind, retain the previous history on the first unexpected idle read and automatically confirm with another incremental read after 100 ms. Accept two matching reads; stop after three changing reads and report the instability. This is a consistency heuristic, not a provider revision guarantee. Failed reads or renewed activity discard the candidate. A shortened prefix alone never proves a new turn completed: preserve the completion barrier through its bounded retries, then reconcile the replacement without marking a new update. Rebuild the graph from accepted history while retaining independently copied descendant evidence.

Compaction is distinct from rewind. Claude's ordinary filesystem SDK read is authoritative for active context. Separately import session records to reconstruct navigation history; do not substitute an imported-store read for active context. The pinned SDK applies filesystem-specific precompaction handling, and real files with repeated compaction can produce different active records through these two APIs. Reads have no default wall-clock work deadline; when an explicit finite budget is injected, each progressively admitted transcript gets its own budget rather than charging discovery or concurrency-slot waiting against it. A compact boundary's explicit `logicalParentUuid` links to the history it summarized. Ask the SDK to read an in-memory navigation projection that follows those links instead of its compact-context rewiring; never write this projection to the provider store. The SDK still chooses the current path and reconstructs streamed blocks, so abandoned rewind paths are not resurrected. Validate that the navigation history contains the active context's exact identities, roles, and payloads, and reject missing or cyclic compaction links rather than silently truncating history. This reconstruction works on fresh startup without caching or persisting message content.

Navigation projection resolves effective transcript content with the pinned SDK's last-write-wins behavior and recognized record types, while retaining repeated versions as separate ancestry evidence. A preserved record's newest parent can describe compacted-context placement rather than historical parentage. Interpret `preservedMessages` and `preservedSegment` as explicit context transformations: recover historical parents from unambiguous local versions or matching ancestor versions reached through validated copy provenance, then reconnect postcompaction continuations in the same candidate projection. Ancestor identities are session-scoped and must be translated into evidenced copies in the current transcript before an edge is projected. Context-only preserved records retain their evidenced selected placement. When the SDK-selected continuation branches inside a preserved prefix, exclude the bypassed later preserved records instead of resurrecting the discarded tail. Older preservation metadata must not reapply a context edge to restored navigation records.

Follow parent identities through the logical ancestry required by the SDK-selected conversation. A parent appearing later in the file, or being re-emitted later, is not a cycle. Validate the candidate ancestry iteratively and detect actual cycles across ordinary and compaction links; report missing or ambiguous evidence rather than selecting an arbitrary old parent or cutting a loop. Unrelated or superseded boundaries do not invalidate the selected path. Ordinary dangling parents retain the SDK-supported truncated prefix; an explicit logical compaction link requires its referenced history. Canonicalization and parent changes apply only to the in-memory navigation projection; fork integrity validation consumes every original physical occurrence.

SDK forks can retain preservation metadata containing parent or ancestor UUIDs even though record UUIDs were remapped. One operation-local record-evidence index serves preservation references, historical parents, anchor association, and continuation evidence. Follow explicit `forkedFrom` lineage through matching record versions instead of using cross-session evidence only for UUID translation. A child with one context-parented version may still have a recoverable historical parent in an ancestor snapshot. Immediate copied-record aliases and sufficient local historical versions do not require the original parent file. Otherwise request only the required ancestor snapshots within the existing read deadline and reuse them throughout the projection. Resolve those source identities through the SDK's provider-wide UUID lookup: fork provenance does not imply that the source file is in the current project's directory. The foreground session catalogue remains project-scoped. Missing snapshots are acquisition requests, not evidence that no historical parent exists. Missing or contradictory evidence after acquisition fails the affected reconstruction without guessed aliases or provider mutations.

Copied-record matching checks meaningful payloads for each recognized record type. User and assistant messages retain exact message-payload checks; attachment, progress, and system records also compare their own data, excluding SDK-remapped envelope fields. Attachment links participate in ancestry and must not compare equal merely because both records lack a `message` field. When translating an ancestor parent, only SDK-omitted progress records may be traversed without a copied local identity. Traverse those chains iteratively, retaining all parent alternatives because omitted progress payloads cannot select a historical version. Reject cycles, conflicting alternatives, and unmapped message or attachment parents rather than converting them into an invented root. An explicit null ancestor parent remains a valid root.

Successful SDK context and complete navigation reconstruction are separate read facts. If a preserved record's matching copy lineage is exhausted and every recorded parent is an evidenced context placement, report an explicit historical-parent gap. A direct summary parent is a context placement for any declared preserved member, including internal attachments, not only the preserved head. Recover such a member's historical parent from matching versions; the metadata's ordered predecessor alone does not prove historical ancestry. Exclusions are scoped to that preserved identity and its declared summary/head anchors, including translated ancestor scopes; an unrelated earlier summary is not automatically excluded. Missing ancestor acquisition, conflicting payload versions or parents, invalid provenance, and other reconstruction errors remain unavailable outcomes. Inspect the other selected paths before admitting a gap so it cannot mask an independently detected contradiction. Validate every SDK context message against the imported effective record's exact role and payload, and require the selected system records, before admitting context-only coverage. Never supply an invented parent to make reconstruction succeed.

Limited coverage is an available context read with an explicit boundary and fixed reason, not an authoritative shorter navigation transcript. Retain its latest context in the actor's history status separately from accepted navigation. If navigation was already accepted, keep that snapshot during limited reads; on cold startup, expose an explicitly labelled SDK-context snapshot. Limited reads cannot move an accepted endpoint, confirm a rewind, settle submission discovery, or prove response completion. Existing bounded completion polling still terminates. Recovery from a context-only snapshot requires bounded matching complete reads, validates active replacement constraints, and rebases pending discovery to the verified representation. Coverage expansion cannot notify a completion; an overlapping completion cycle keeps its bounded barrier and suppresses unread-completion inference until that cycle ends. A previously complete snapshot resumes ordinary complete-history reconciliation when full coverage returns.

Show limited coverage with a compact history-gap indicator before the catalogue's aligned displayed-message and branch counts, and a history-gap notice in the graph. Opening a discovered session continues through normal identity and ownership checks. Fork admission requires verified history, and provider-side source/copy validation remains mandatory. Context-only snapshots do not supply cross-session graph correspondence; retain recorded relationships without applying them to a context-only path. Previously accepted complete navigation may continue using its independently validated relationships while a limited read is outstanding. This conservative snapshot retention is process-local and does not persist conversation content or alter provider transcripts.

Conversation history and integrity issues are persistent, non-blocking navigator status. Opening a usable graph does not automatically display an error dialog. Both the selected root and its graph expose current details through `e details`, shown between Refresh and About only when details exist. Dismissing the scrollable, copyable dialog leaves those details available until the underlying issue resolves. Failed actions and retries that cannot open a graph still report errors.

`--diagnose-history` instruments that same production Claude read operation with an optional, operation-local collector. Record the decisions where they occur; do not maintain a second reconstruction algorithm for diagnostics. Reports are constructed from an allowlisted schema containing anonymous identities, counts, fixed reason/field codes, and equality flags. Never serialize raw records, exceptions, arbitrary payload keys, paths, original UUIDs, or conversation hashes. Bound trace storage and identify omitted events explicitly while retaining the terminal failure classification.

Diagnostics distinguish `Limited` from complete `Available` and `Unavailable` outcomes. A limited report includes the readable context counts and the anonymized `history-gap` reconstruction failure; it does not present a successful context read as total read failure.

Run headless diagnostics in an owned, read-only subprocess with stdout/stderr redirected and a separate IPC report channel; Bun worker-thread stdio capture does not reliably isolate library logging. Validate the report schema again before printing it, and validate the private Execute/Cancel request protocol in the child. The child owns its read scope, finalizes before sending its report, awaits IPC delivery, and disconnects for natural exit. Cancellation, SIGTERM, or parent disconnect interrupts its read and awaits scoped finalization. Diagnostic work and exit observation have no default deadlines; explicit finite execution and cleanup observation budgets may be injected. The parent retains actual cleanup separately from its observers, permits cooperative exit before timed SIGTERM/SIGKILL escalation, and requires an actual exit event or established exit state. A report or successful signal dispatch is not exit evidence. An explicit observation timeout reports unconfirmed cleanup without losing late exit observation. Diagnostic composition bypasses the renderer, application actor, persistence repository, terminal supervisor, and provider mutations. Build identity comes from a packaged revision stamp or the application's own checkout, never the diagnosed project's Git repository. ## One Application Actor In One Foreground Process

Each invocation has one application-state actor. Application view publication is the production reporting authority: while viewing a tree, report the same aggregate status as that tree's root-list row; while viewing a stock terminal, report only that session; while viewing the roots list, report idle. Unrelated trees must not override the displayed tree or terminal. Herdr's CLI accepts idle, working, blocked, and unknown: map Live and New updates to idle with descriptive messages, Working to working, and Needs user to blocked. Remove Herdr's pane-specific environment variables from every nested provider process, including both Codex metadata app-servers and interactive sidecars, not only PTYs. Use the same environment builder at each spawn while preserving provider authentication and unrelated user-hook settings. Otherwise native session hooks can claim the outer pane and cause Herdr to reject subsequent claude-tree lifecycle and resume reports from a conflicting owner.

Use one status priority and one marker renderer across session endpoints, root-list rows, and both Open leaf and Jump to Leaf pickers: Needs user (red dot), Working (animated braille), New updates (yellow dot), Live (green dot), then inactive (muted hollow dot). Working outranks unread updates, including when an unread session starts another turn; merely navigating the tree does not mark a terminal as viewed. Live requires a terminal, not just a persisted session. Open pickers refresh their status markers without resetting selection, and root-list working indicators animate independently of provider refreshes.

Claude's current adapter launches only the stock TUI through that filtered PTY boundary; its lifecycle hooks add a loopback listener and a private token, not a sidecar or subprocess. The pinned SDK session discovery, reads, imports, and filesystem forks do not launch Claude or execute its user hooks. Audit that assumption when upgrading or adding SDK execution APIs: any new provider subprocess must receive the same filtered environment. Do not change global `process.env` or remove unrelated user hooks to isolate Herdr ownership.

Attach the current workspace ID and `claude-tree [--codex] --resume WORKSPACE_ID PROJECT` argv to state reports, including when the displayed destination changes without a status change. The first argument is a PATH command name; reject apostrophes, control characters, and commands exceeding 64 arguments or 8 KiB before sending resume metadata. Invalid argv never suppresses ordinary activity reporting. Resume requires Herdr 0.9.2+. Herdr does not receive PTY handles: its restart launches a fresh invocation using saved semantic navigation, not previous emulator state.

## Input And View Ownership

The application has two modes: navigator and embedded terminal. In terminal mode, input belongs to the selected agent except for one configurable host escape chord. The initial default is `Ctrl+Space`, selected explicitly for returning to the navigator.

Avoid intercepting ordinary agent keys. Host shortcuts should be mode-specific, visible to the user, and configurable when practical.

Terminal mode keeps a persistent bottom bar with left-aligned `c/t · Ctrl+Space back`, using the navigator footer's text styling and full-width background. The keybinding is clickable. Reserve that row in the emulator and PTY dimensions, including for hidden terminals and on resize, so the control never covers provider output.

## Releases Are Compiled npm Packages

Binary releases use one build/package script and an explicitly dispatched workflow with a version input. Run the existing regression suite without release smoke tests, package all supported platforms, publish their npm tarballs before the exact-version launcher, then create the Git tag at the dispatched source commit. Retain basic version/tag conflict checks, not custom publication recovery, artifact manifests, GitHub Release staging, or standalone downloads. Never overwrite npm versions or move release tags; inspect partial publications before releasing a new version. Nix remains a separate optional source installation, not the release pipeline. Provider executables remain external dependencies.

## Shared Working Tree Is Deliberate

Every agent process starts in the same project directory. This allows branches to observe and build on the same filesystem state, but it also permits simultaneous edits and conflicts. The application should communicate status accurately and must not claim branch-level file isolation or silently create worktrees.

Future agents have latitude in UI composition, state modeling, testing strategy, and dependency choices. Changes should be judged against the goals in `project-goals.md` and the behavioral constraints above.
